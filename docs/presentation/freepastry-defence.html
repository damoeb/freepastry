FREEPASTRY · JAVA25-UPGRADE · NOVEMBER 2026

How FreePastry defends itself

How the Pastry overlay routes a message, what certified mode adds, which attacks the hardening stops, and which it does not stop yet.

This deck explains the algorithm first (ring, prefix routing, the node stack), then the two modes and the threat model, then what the 2026 hardening stops for outsiders and for certified insiders, and finally the open gaps and the plan (waves B to D). Status as of 27 November 2026 on the java25-upgrade branch.

HOW IT WORKS · THE RING

Every node and every key sits on one ring

Node ids and keys are 128-bit numbers on a circle. A message for key k goes to the node whose id is numerically closest: the root of k.

Each node knows its nearest neighbours on both sides (the leaf set) and, in a routing table, a few distant nodes for every id prefix.

Every hop fixes at least one more hex digit of the key, so a message needs about log₁₆ N hops: five hops for a million nodes.

Pastry places nodes and keys in the same 128-bit id space, drawn as a ring. The root of a key is the live node whose id is numerically closest. The source sends towards the key; each hop forwards to a node that shares a longer id prefix with the key, and the last hop lands in the root’s leaf set. Applications such as Past and Scribe build on this: Past stores an object at the root and its leaf-set neighbours, Scribe roots a multicast tree at the topic’s root.

Row r of a routing table holds nodes that share r digits with this node, one for each possible next digit. If a hop is down, a node picks another entry with the same prefix or a leaf-set neighbour.

The routing table has one row per prefix length and 16 columns, one per next hex digit. A node forwards to the entry that extends the shared prefix with the key by one digit; when the key falls within its leaf set, it delivers to the numerically closest neighbour. This is why routing is fast, and also why it is sensitive to who fills those table slots: that comes back on the limits slide.

HOW IT WORKS · THE NODE STACK

Each layer checks what passes through it

Applications
Past, Scribe, Glacier, PeerReview

Content hashes, owner-signed Glacier manifests, Scribe sources must match the previous hop, certificates checked against the CA

Pastry overlay
routing table, leaf set, join

Only verified handles are admitted; join answers come from authenticated senders; ready state changes on the selector thread only

Liveness and priority

Pings carry a random nonce; trackers and big-message buffers are bounded; TLS reads are fair per selector turn

Identity binding (certified)
(id, address, epoch)

A certificate proves the id; only a connection this node dialled proves the address

TLS 1.3 (certified mode)

Trust store holds only the CA; node certificates carry proper extensions and random serials

Wire: TCP and UDP

10 s handshake deadline, 32 handshakes per IP, bounded readers that drop bad input instead of crashing

FreePastry is a stack of transport layers under the Pastry node, with applications on top. Everything runs on one selector thread, which is why a single uncaught Error used to stop every node in the JVM. Each layer now bounds what it keeps and drops what it cannot verify. The identity and TLS layers are what certified mode adds.

USE CASE · ENTERING THE NETWORK

A new node joins the ring

New node N

Bootstrap B

Root R

1 · TLS, N dials

2 · JoinRequest

4 · reaches root

5 · accepted: leaf set and table rows

6 · probe each handle at its own address

  1. N holds a CA certificate with a random id and dials a known bootstrap B over TLS.
  2. N sends a JoinRequest for its own id.
  3. Pastry routes it towards N’s id; every hop adds a row of its routing table.
  4. The root R, the existing node closest to N’s id, accepts the request.
  5. N adopts the answer only from an authenticated sender.
  6. N probes every returned handle, announces itself to its leaf set and turns ready.

Joining reuses routing: the JoinRequest is a message addressed to the new node’s own id, so it ends at the node that will become its neighbour. Steps 5 and 6 are certified-mode checks added in 2026; plain mode takes the answer as it comes. Still open: a malicious bootstrap or root can answer with colluders (wave C4 adds several bootstraps and a density test).

USE CASE · SENDING A MESSAGE

A message travels hop by hop to the root of its key

Sender S

The app calls route(key, msg). S picks the table entry that shares the longest prefix with the key and queues the message by priority.

Hop

Receives over TLS: the previous hop is the id in its certificate. Apps on the hop may see the message on the way (forward).

Hop

If the next node is down, it picks another entry with the same prefix. Liveness comes from pings with a random nonce.

Root R

The key falls in its leaf set, so it delivers the message to the app, which can ask which node it came from.

Each hop drops what it cannot read, bounds what it keeps, and in certified mode binds the sender to its certificate.

Not yet: a malicious hop can drop or misroute the message. Redundant routing and a routing failure test come in wave D.

Messages are routed, not sent end to end: each hop decides the next one from its own routing table. That keeps state small and routes short, but it means every hop on the path must be honest for the message to arrive. The hop-by-hop acknowledgements only show that the next hop got the message, not that the root did.

USE CASE · STORING AND FINDING AN OBJECT

Past keeps copies next to the object’s id

  1. The object’s id is the SHA-256 hash of its content (in Glacier: of the owner’s key and the object’s name).
  2. The insert is routed to the root of that id.
  3. The root and its nearest leaf-set neighbours store replicas and acknowledge; the insert succeeds once enough of them have.
  4. A lookup is routed towards the id and answered by the first replica it meets.
  5. The reader checks the hash and rejects a wrong answer.

Not yet: one malicious replica can answer a lookup of mutable content (waves B2 and C6).

Past is the storage layer on top of Pastry; ExpiringPast adds leases capped at a year, and Glacier adds erasure-coded, owner-signed archives. Because replicas sit on the leaf set of the root, the set heals itself when nodes come and go: replication moves copies to the new neighbours.

DEFENCE · TWO MODES

Plain mode trusts the network, certified mode proves who is talking

Plain modeCertified mode
Who can joinAnyone who can reach a nodeNodes holding a certificate from the deployment’s CA
Who sent a messageWhatever the message saysThe TLS certificate of the previous hop
Where a node livesTaken from its handleProven only by a connection this node dialled itself
Join answersTrusted as they arriveOnly from an authenticated sender; every handle is probed first
Meant forTrusted networks and the simulatorUntrusted networks

The rest of this deck assumes certified mode. In plain mode, anyone is an insider.

Plain mode is the historic FreePastry behaviour: a node believes the ids and addresses written in messages. Certified mode (CertifiedSocketPastryNodeFactory) runs every connection over TLS 1.3 with CA-issued node certificates and admits a handle only for the exact id, address and epoch that presented the certificate. Plain mode is now documented as trusted-network-only; the hardening against crashes and memory exhaustion applies to both modes.

DEFENCE · THREAT MODEL

Two kinds of attacker

Outsider

Any host on the internet, without a certificate.

  • Sends malformed or truncated bytes
  • Spoofs UDP datagrams and node handles
  • Opens many slow or half-open connections
  • Floods from many addresses

Certified insider

A minority of nodes with valid certificates, possibly colluding.

  • Lies about ids, addresses and senders
  • Answers requests it was not asked
  • Forges protocol messages and certificates
  • Steers joins, routing and replicas

Out of scope: a compromised CA, a majority of malicious nodes, an attacker who controls the whole network path.

The 2026 analysis assumed certified mode on an untrusted network. Outsiders can reach any node but hold no certificate. Insiders hold a real certificate, so TLS alone does not stop them; what matters is that they cannot claim to be someone else or live somewhere else, and that protocols do not believe what an insider writes into a message.

DEFENCE · STOPPED: OUTSIDERS

Outsiders can no longer crash a node

AttackDefence now
Malformed or truncated messages crash the nodeBounded readers and fuzz tests; a bad datagram is dropped, a bad socket closed
A Glacier response sent as a request stops every node in the JVMDropped and logged; a test forbids new Error( in main code
Spoofed handles fill memory until it runs outWeak handle cache; identity and liveness tables are size-bounded
Slow handshakes hold sockets open (slowloris)10 s handshake deadline, at most 32 handshakes per IP
A burst of tiny TLS frames overflows the stackA bounded read loop, at most 64 reads per socket per selector turn
A forged PONG marks a dead route aliveEach ping carries a random 64-bit nonce
A node relays traffic to any addressAddress policy on every hop: no wildcard, multicast or self

Every row was reproduced first: a test that failed on the old code for the right reason, then the fix. The two most dangerous were kill switches: any Error on the selector thread destroyed the whole Environment, which stops every node in that JVM. One forged Glacier message, or a burst of about 1,600 one-byte TLS messages, was enough.

DEFENCE · STOPPED: CERTIFIED INSIDERS

Insiders can no longer pose as someone else

AttackDefence now
Advertise a trusted node’s id at the insider’s own addressA handle counts only for the exact (id, address, epoch) that showed the certificate; others are probed first
Claim an honest neighbour’s address before TLS (eclipse)Only a connection this node dialled proves an address; a claim never marks a node dead
Answer a joining node with a forged leaf setAnswers only from authenticated senders; every handle probed before it enters the leaf set
Forge Glacier manifests or squat fragmentsOwner-signed manifests; storage ids derive from the owner’s key
Store fake Past content under a content-hash idThe hash is checked on insert, cache and lookup
Forge Scribe acks or unsubscribes, or publish as someone elseThe source must be the authenticated previous hop; acks only for open subscribes
Frame a node with a forged PeerReview certificateCertificates must come from the CA for the asked id; a valid one is never replaced

An insider has a real certificate, so these defences are about binding what it says to what it proved. Also fixed: the CA tool now draws ids from SecureRandom and refuses a requester-chosen id unless the operator allows it, logs every issuance, and issues a v3 CA certificate. Leaf-set broadcast and join senders are being bound to the authenticated hop right now (wave B, in progress).

An incoming connection proves only M’s id. Only a connection V dialled proves an address, so B stays bound and M is probed at its own address before it is admitted.

This was finding O1 of the overlay analysis, fixed in wave A. The test builds a certified ring with real TLS and a test CA: on the old code node A marked the real B dead; now B stays in A’s leaf set and M’s handle at B’s address is neither authenticated nor admitted.

LIMITS · NOT STOPPED YET

Insiders can still steer routing and answers

AttackWhy it still worksPlanned fix
Colluders fill a victim’s routing tableSlots go to the lowest round-trip timeD1: constrained table, redundant routing

A wrong node answers a Past or Glacier requestResponses match by counter onlyB2: random ids, expected responder

A node on the path fakes livenessThe nonce stops only off-path sendersC5: HMAC per peer, windowed RTT

Many addresses flood one nodeNo per-peer budgets or fair queuingC1–C3: budgets and token buckets

Other known limits: a hop still relays to any routable non-Pastry host that passes the address policy; anyone may refresh a Past object up to the lease cap; NAT nodes can only run plain mode; any node can subscribe to a multiring gateway topic. Plain mode trusts its network by design. The letters refer to the roadmap on the next slide.

TAKEAWAYS

Where FreePastry stands

1

Outsiders can no longer crash a node or exhaust its memory.

Bounded readers, tables and loops; no remote input reaches an Error.

2

Certified insiders can no longer pose as another node.

Ids, addresses and senders are bound to what TLS proved.

3

They can still steer routing, joins and answers.

Waves B to D close that, with secure routing as the largest step.

Use certified mode on any network you do not fully trust. Until waves C and D land, treat lookups of mutable content and routing to a single root as best effort against a colluding minority.
